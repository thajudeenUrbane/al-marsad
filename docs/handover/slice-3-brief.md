# Slice 3 brief — the scholars' review queue

Context: docs/13-platform-direction.md §2 (D2) and §4 slice 3; docs/06-scholarly-methodology.md §3 (workflow, roles, scholar attention); docs/05-ux-architecture.md §6.3; docs/handover/maintainer-answers-1.md (section "Scholars and review"). Read docs/handover/slice-2-summary.md first: slice 3 starts only after slice 2 is merged. Do not read chat history; this file is the brief.

## Goal
Two or three scholars, working on a phone or a laptop, can review **50 claims in one sitting**. Each decision is recorded in the graph with the reviewer's name and date. After a rebuild, the public pages show the new status and who reviewed it.

## What the maintainer told us (15 October 2026)
- 2–3 historical scholars now, 3–6 h/week each, on **phone and laptop**. More later: one scholar now, many later, with no redesign (doc 13 D2).
- They check four things: the report exists in the source; the chain is sound; the summary is fair; who is who.
- Reviewers are **named on every claim** they review. Disagreements go to **the board, which votes** (the board is not formed yet).
- First board: Sunni, across the four madhhabs, coordinated initially by Shāfiʿī scholars. This is a **declared default**, stated publicly, not presented as neutral.
- The 50 Stories were **generated by AI**. They are the first thing scholars should review.

## Rules for all of slice 3
- **Only a named human moves a claim.** `proposed` → `accepted`, `rejected` or `under review` happens only through a recorded review decision by a reviewer on the roster. Software never changes a status on its own.
- **No acceptance without a real source.** A claim whose only basis is the AI-generated 50 Stories document can be accepted only if the reviewer cites a real source (work and location, e.g. "Ibn Hishām, Sīra, vol. 1 p. 480"). Record the citation with the decision. Never invent one.
- **Model it honestly.** `mrs:Evaluation` is for gradings recorded in a work and requires a cited Passage and a tradition. Use it only where that is true. For a platform review decision, add a minimal `mrs:ReviewDecision` (⊑ `crm:E13_Attribute_Assignment`, `prov:Activity`) with a SHACL shape: reviewer (1), target (1), decision (accept / reject / needs discussion), the checks performed (from the four above), note, date, optional source citation. Never fake a Passage to satisfy `EvaluationShape`.
- **One Tradition instance** for the first board's lens, labelled as the declared default (wording from maintainer-answers-1.md). Nothing else may claim to be neutral.
- **The roster is maintainer data.** `review/roster.csv`: reviewer ID (minted with mint_id.py), public name, role (doc 06 §3.1), scope (period/topic), granted date, granted by. It ships **empty** with a header row only, because names come from the maintainer. No contact details in the repo.
- Every UI string is an i18n key from day one (see Open question 1). Logical CSS. Same weight discipline as slice 2.
- Never upgrade a status by hand. Never invent names, sources or dates. Commit on the current branch; message ends with the attribution lines you are given. Do not push.

## 3a — data model, queue and importer (no UI)
1. `ReviewDecision` class and shape in marsad.ttl / shapes.ttl (or relations.ttl if that is where such things live), plus the Tradition instance. Keep each source file valid with validate.py.
2. `review/build_queue.py`: turns every `proposed` assertion into review units, batched **by story** (50 Stories), then **by person**, then by source file. Each unit has the claim in plain words, its basis passage verbatim, its current status and any earlier decisions. A second queue holds the identity rows marked needs-review in identity.csv, as `mrs:IdentityAssertion` candidates ("same person?" / "different people?").
3. `review/import_decisions.py`: reads decision files (JSON, schema documented in the handover), checks each reviewer is on the roster and in scope, rejects anything malformed or out of scope with a clear message, then writes `ontology/corpus/reviews.ttl` and applies the status change. Re-importing the same file changes nothing (idempotent). `build_graph.py` must conform afterwards.
4. Tests with a **throwaway test roster in the test folder only** (clearly fake names like "Test Reviewer A"), covering accept with citation, accept without citation on a 50 Stories claim (refused), reject, needs discussion, out of scope (refused), and re-import.

## 3b — review pages for phone and laptop
1. `review/build_pages.py` → `review/dist/` (gitignored): one page per batch. Each card shows the claim, the source passage beside or below it, and Accept / Reject / Needs discussion as large tap targets with keyboard shortcuts on laptop. It also has the four checks as tick boxes, a note field, and a source-citation field that is required for accepting a 50 Stories claim.
2. Decisions are kept in the browser while working, so a lost connection loses nothing. **Send my decisions** produces one decision file, shared with the phone's share sheet where available, otherwise downloaded. The scholar sends it to the maintainer (WhatsApp or email). The maintainer drops it in `review/inbox/` and runs the importer.
3. Works offline once loaded; no account and no server.
4. Usability check: time how long 50 claims take on a mid-range Android phone (emulated in Playwright) and record it in the handover.

## 3c — board items and credit (only after 3b is used by a real scholar)
1. "Needs discussion" items listed on a board page, with each reviewer's note. Vote recording is added once the board exists (maintainer: "later").
2. A public contribution ledger: per reviewer, claims reviewed and dates (doc 06 §3.2 point 5).
3. Optional: a hosted way to send decisions (Cloudflare Pages Functions with a small database, behind Cloudflare Access) once the site is on Cloudflare. It feeds the **same importer**, so nothing else changes.
